Formally prove any Java change in one command

Point Claude Code at a pull request or a commit. It states what the change must do and must keep, proves each claim from the compiled bytecode in an unattended loop, and shows you an input wherever a claim fails. You write no specification.

Install the plugin

claude plugin marketplace add pilifs/in-the-loop
claude plugin install in-the-loop@in-the-loop

Then, in Claude Code

/in-the-loop:prove-java-change <pull request or commit>

Runs on Fable 5.2 at high effort, on Linux with 8 GB of memory or more. Nothing leaves your machine unless you agree to send a contribution back.

Under the hood

Your code is the spec

Nobody writes a specification. Each proof takes its statement from something your project already has, and checks it against the bytecode your build produced.

Previous version →

Regression proof

The new method behaves as the old one on every input, outside the change you meant to make. Or here is the input where it doesn't.

Types →

Behavioural contract

Every input of a finite method (enums, booleans, records, sealed types) is executed, before and after, and the outcomes are diffed.

Bytecode →

Capability and boundary contracts

What the module can reach (clock, network, reflection) and where Spring enters it: routes, listeners, advice, and what each one reads, writes and sends.

The change's intent →

Property proof

One line stated beside the code and proved on every input. The plugin drafts these from the change and its history. You confirm them in plain words.

91,049 lines of Rust

jvmcontract, the verifier

A class-file reader, a bytecode interpreter, and its own bounded model checker over a bundled SAT solver (CaDiCaL), with 17 JDK classes modelled. It derives contracts without a JVM and builds its proofs without javac. JBMC stays available as a second engine.

The orchestration around it

It prepares a change as an example with pinned sources, runs each proof as a queued job under a memory and CPU cap, keeps a receipt per attempt, and drives the unattended loops.

  • A proof where JBMC ran out of memory. An encoder fast path that JBMC could not finish in 2.8 GB is proved equal to its previous version in 7 s and 76 MB. The buggy variant is refuted in 1.1 s.Example 142
  • Two engines, one answer. On the 35 recorded obligations both engines decide, none is decided differently.Engine coverage
  • Witnesses you can run. A counterexample is shrunk to a small input, replayed in the interpreter, then run on a real JVM.
  • Proofs are cached. The key is a SHA-256 over the method's code, the tool, the JDK and the models. A rerun with nothing changed takes 66 ms.

JAR → JAR

Compare two builds, with nothing written by hand

jvmcontract compare takes the compiled classes of two builds. It works out which old method became which new one, checks every HTTP route and message listener by the calls it makes, in order, and proves each changed method against its predecessor.

It ends with what a person decided, what it asks of one, and what it assumed. In this run a refactor adds a cent per item, and the proof finds it at the route and in the kernel.

A release works the same way. Example 285 ran on the published Spring Boot 2.7.17 and 2.7.18 JARs, each on its own dependencies.

How it works

Not "just another skill"

The skill itself is 97 lines. It installs a hash-checked copy of the whole verification repository on your machine, then runs a proof loop on it that can extend the verifier.

A closed loop that improves itself

  1. Your changebecomes an example, with its claims frozen before any proof runs.
  2. The proof loopruns it against your local copy of the library.
  3. A gap is closedwhen the verifier can't model your code yet: the loop extends it and commits.
  4. The library is largerso your next run starts with what this one needed.

each run extends your local copy, and the next one is cheaper

This happened on the first target. On 2026-11-14 every proof task of example 285 stopped at something the verifier could not model: a parameter of an interface type, and two releases with different dependencies. The next day the proof loop extended jvmcontract for both in three commits, reran the unchanged claims on the same JARs, and all four came out as expected. Read the closed gaps →

The four steps

  1. Set up and measure

    A subagent installs a released copy of the repository, checked against a SHA-256 the skill carries, and measures your machine for a memory budget.

    You confirm.

  2. State the claims

    It pins the change to two exact commits, sizes it against the closest past examples, writes each claim in full, and runs the change once on a JVM.

    You confirm the claims and the estimate.

  3. The moonshot

    Prove it

    A fork of the session runs unattended on one line: Formally prove example NNN as elegantly and efficiently as possible. Fable 5.2 works out what stands between the library and your code, closes it, and proves the claims. It may not change a claim to fit a result.

  4. Report

    Each claim comes back established, refuted with an input replayed on a JVM, or left open with the reason, under stated bounds. Then it offers to send what it added upstream.

    You decide.

Step 3 has no acceptance criteria to meet, so the session that started it stays outside as its conductor. When the loop fills 600k tokens of context without a commit, the conductor reads the transcript, the commits and the jobs, and decides whether it is working or stuck.

How it was built

The development process

The repository went from empty to 167,128 lines of code in 14 working days. Almost all of it was written by models working alone, and every session is public.

From scratch, on one subscription

The first commit is dated 2026-10-24. By 2026-11-15 there were 749. One Claude Ultra plan paid for all of it.

It is vanilla Claude Code. The repository configures no MCP server and no outside plugin, and all 25,842 recorded tool calls went to built-in tools. 22,655 of them were Bash.

Every turn is on the record

A hook captures each turn. It goes to a local Langfuse for browsing, and a redacted transcript is published with the commit it produced.

Each commit message links its session and carries the SHA-256 of the log, so anyone can download a log and check it. 742 commits have a trace.

The index of all 113 sessions →

Mostly unattended, in one VM

590 of the 742 traced commits were made inside a loop run: 34 loops, 109 runs and 350 cycles. A loop commits locally and never pushes.

They ran in a VM with 30 vCPUs and 105 GiB of memory, with no swap. Each loop and each proof gets a hard memory cap, so one that runs away is killed alone.

Every loop, run and cycle →

Layers of agents and scripts

  1. /prove-java-changeFable 5.2, with an Opus subagent for setup

    Orchestrates the four steps and conducts the proof loop from outside.

  2. feature-loop.shFable for moonshots, Opus 5.5 for briefs

    Instruction, commit, compact, repeat. A moonshot repeats one open-ended line. A brief is a file of items with acceptance criteria. A cycle with no commit stops the loop.

  3. run-streams.shseveral loops at once

    Runs a brief's streams side by side, each in its own workspace, checks the merged tree every hour, and merges them at the end.

  4. The verification loopSonnet 5.5

    Proofs never run inside a development session. A session queues them as jobs, and a fresh session runs the queue under memory and CPU limits and brings the results back.

  5. sync.py and the tools beside itPython, no model

    Hooks that capture and redact each turn, stamp each commit with its trace, publish the logs, and add up the metrics on this page.

Contribute back

Your run can make the next one easier

When a proof needed something new of the verifier, that part helps the next person more than it helps you. The plugin offers to send it upstream, and sends nothing until you agree.

Send an example

Every example is welcome. The ones that extend jvmcontract are worth the most: a new JDK model, a checker extension, a new way to prepare a change.

Step 4 prepares the pull request. Your machine's records stay behind, and a check looks for anything that names your user or host before it is pushed.

Before you run it

Questions

What does it need?
  • Claude Code, on Fable 5.2 at high effort
  • Linux on x86_64 or aarch64. It has run on Ubuntu 24.04 and 26.04: on a machine, in a VM and under WSL2
  • At least 8 GiB of memory, 2 CPUs and 10 GiB of free disk. 16 GiB, 4 CPUs and 25 GiB are comfortable
  • Python 3.11, git, jj, JDK 25 and Rust 1.82. Step 1 installs what it can without sudo and tells you the rest

JBMC is optional: without it, only the verifier's own checker decides.

What can't it do yet?
  • The change must be public: a commit on github.com or a published JAR. A private repository or uncommitted work has no route of its own yet. A small change can be copied in as a fixture.
  • Proofs are bounded. Arrays and loops are checked up to a stated bound, 8 elements by default, and the report names it.
  • The verifier's own checker has no floating point, and models part of the JDK. What it can't model is left open with the reason. It is never reported as a pass.
  • It is new. One of the 16 Spring security fixes in the examples is proved so far.
All limits of the verifier →
How long does a run take, and what does it use?

One measured run, example 285: the proof loop took 2 h 59 min, made 481 model calls, wrote 467,660 tokens, and used 7,956 CPU seconds of proof. At API list prices that is $65.63. Your change will differ, so step 2 gives you an estimate in hours and tokens and waits for your answer.

Does anything leave my machine?

No. The copy the plugin installs has tracing and publishing switched off, and it never pushes. The one exception is a contribution upstream, as a pull request you agree to first.

What does "established" mean?

The claim holds for every input within the bounds and assumptions the report states, not for a sample of them. A refuted claim comes with an input, run on a real JVM. A claim the tool could not decide is left open and says why.
