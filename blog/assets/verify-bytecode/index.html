Formal verification for Java pull requests

Point it at a pull request. It compiles both sides, proves what changed from the bytecode, and shows an input wherever the behaviour differs. No tests or specifications to write.

Optional: use the included /add-tla-model skill to add custom invariant models that extend formal verification to your most critical business logic.

curl -fsSL https://terminalvalue.net/verify-bytecode/install.sh | bash
claude plugin install jvmcontract --marketplace pilifs/in-the-loop

Installs both skills, the verifier and TLC. JBMC, a JDK, gh and jq are checked, not installed. Read the script.

How it works

From pull request to report in six steps

  1. Fetch

    Reads the pull request and checks out both sides.

  2. Scope

    The changed files, their module, and every changed method.

  3. Build

    Both versions, with the project's Maven or Gradle build. Claude Code asks first.

  4. Prove

    Each method with the proof its shape allows, under a time and memory budget.

  5. Diff

    The module's capabilities and public API, before and after.

  6. Report

    Verdicts, the inputs behind them, and every command.

What it proves

Three verdicts, and no silent passes

If the tool could not check something, the report says so and says why.

Verified

The proof covered every input within the stated bounds.

Violation

A concrete input, replayed. For a regression proof, that is a behaviour change, intended or not.

Unverifiable

The tool gave no verdict and says why. It is never reported as a pass.

TLA+ models

Check your own invariants

Run /add-tla-model in your project and say the rules in plain words. It builds a model around the code that decides what happens next, and checks them.

/add-tla-model "no two confirmed orders share a seat"

  1. Find the logic

    The code that decides what happens next. If it's spread out, the skill proposes an extraction and asks first.

  2. Derive it

    Its behaviour comes from the bytecode, so the model runs what the code does.

  3. Model the system

    One action per transaction, message or timer, plus your rules.

  4. Check every build

    TLC shows the steps that break a rule. The build fails when the logic changes, until the diff is reviewed.

FAQ

Questions

What can't it do?
  • Arrays and loops are checked up to a stated bound.
  • Methods over strings, collections and objects get no per-method proof.
  • Some 64-bit arithmetic can exhaust the solver.
  • A TLA+ model is partly hand-written, and is checked within small bounds.
All limits and measured costs →
What does it need?
  • Claude Code
  • A JDK, with Maven or Gradle unless the project has a wrapper
  • gh, logged in, plus git and jq
  • JBMC, for regression and property proofs

The installer sets up Rust and TLC.

What does a passing TLA+ model prove?

That within its bounds, no ordering of the modelled actions breaks your invariants. It does not prove the Java correct: the decision logic comes from the bytecode, but the rest of the model is hand-written.

Does it write to my pull request?

Only with --post. Otherwise nothing is written anywhere but a working directory you can rerun from.
